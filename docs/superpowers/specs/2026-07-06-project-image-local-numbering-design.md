# 项目内图片编号设计

## 背景

当前工具使用 `evidence_images.id` 作为真实图片 ID。该 ID 是 SQLite 全局自增主键，因此不同项目上传图片时 ID 会连续增长。界面和导出文档中的图号已经按章节显示为 `图A-x-y`，但内部 token 仍是 `[[FIG:全局图片ID]]`。

用户希望图片编号在每个项目内从 1 开始，并且删除图片后自动重排；重排后，结果记录中显示的图片引用编号也应自动刷新。

## 设计目标

- 界面和导出文档使用项目内编号，不暴露全局图片 ID。
- 每个项目的图片编号从 1 开始。
- 删除图片后，项目内编号自动重排。
- 结果记录中显示的图号随图片排序和删除操作自动刷新。
- 内部仍保留全局唯一 `evidence_images.id`，用于数据库主键、外键和稳定引用。
- 不破坏现有 DOCX 导入、图片替换、导出、校验和交叉引用逻辑。

## 非目标

- 不把 `evidence_images.id` 改为每个项目从 1 开始的主键。
- 不把 `cross_references.target_image_id` 改成复合键。
- 不要求历史导出的 DOCX 在 Word 外部自动更新；重新导出时按当前项目数据生成最新图号。
- 不改变用户上传图片文件的物理存储路径规则。

## 推荐方案

采用“双编号”机制：

- `evidence_images.id`：内部全局 ID，保持现状。
- `project_image_no`：项目内显示编号，按项目所有图片的稳定顺序动态计算。
- `figure_label`：章节内图号，继续按章节和章节内排序显示为 `图A-x-y`。

其中 `project_image_no` 用于用户理解“本项目第几张图片”；`figure_label` 用于结果记录、图片卡片、导出题注和 Word 交叉引用。

第一版优先采用动态计算，不新增数据库持久字段。动态计算来源为同一项目下所有图片，按章节顺序和章节内 `sort_order` 排列后从 1 开始编号。

## 数据流

### 上传图片

1. 后端保存图片文件并创建 `evidence_images` 记录。
2. 数据库生成全局唯一 `id`。
3. API 返回图片时动态补充：
   - `project_image_no`
   - `figure_label`
4. 前端不直接展示全局 `id`。

### 插入图片引用

1. 前端引用下拉仍绑定真实 token：`[[FIG:全局图片ID]]`。
2. 录入框显示用户可读图号：`图A-x-y`。
3. 保存章节时，显示文本转换回真实 token。
4. `cross_references.target_image_id` 继续保存真实全局 ID。

### 删除图片

1. 删除 `evidence_images` 记录和对应图片文件。
2. 数据库外键将相关 `cross_references.target_image_id` 置空。
3. API 再次返回图片列表时，项目内编号和章节图号自动重排。
4. 前端根据最新图片列表刷新录入框显示文本。
5. 若结果记录中仍存在已删除图片的 token，校验仍按断链引用处理，提醒用户删除或替换该引用。

### 导出 DOCX

1. 导出时按当前章节图片排序生成 `图A-x-y` 题注。
2. Word 题注继续使用 `SEQ 图A-x-` 字段。
3. 正文交叉引用继续根据真实图片 ID 找到目标书签，再显示最新图号。

### 导入 DOCX

1. 导入解析继续识别 `图A-x-y` 题注。
2. 解析阶段使用临时 token：`[[FIG:import:A-x-y]]`。
3. 确认创建项目后替换为真实全局 ID token。
4. API 展示时再动态生成项目内编号和章节图号。

## 前端表现

- 图片卡片显示：
  - 主图号：`图A-x-y`
  - 可选辅助信息：`项目内图片 N`
- 引用下拉显示 `图A-x-y`，不显示全局 ID。
- 结果记录文本域显示 `图A-x-y`。
- 删除图片、调整排序、重新加载章节后，文本域中的图号显示自动刷新。

## 错误与边界

- 已删除图片仍被正文引用时，保存不会把引用自动改到其他图片，避免误指向。
- 校验应提示断链引用，用户需要删除引用或重新插入正确图片。
- 若筛选证据图片，只影响展示，不影响完整图片列表的编号计算。
- 若图片排序发生变化，显示图号会变化，但内部引用仍指向原图片 ID。

## 实施落地说明

- 后端未新增持久字段，`project_image_no` 由 API 按项目内章节顺序、图片排序和真实 ID 动态计算。
- 前端证据图片卡片主标签继续显示章节图号 `图A-x-y`，辅助状态显示“项目图片 N”，不展示全局 ID。
- 删除图片后，当前章节和已缓存章节的 `project_image_no` 会同步重排，避免章节切换后看到旧项目内编号。
- 结果记录显示优先使用当前图片列表中的 live 图号；如果 token 对应图片已不存在，则显示原始 token，并把目标图片 ID 保持为 `null`，避免旧 `display_text` 或 token 数字把断链引用伪装成有效图号。
- 导出 DOCX 继续使用真实图片 ID 找书签目标，但可见题注和正文 REF 显示均来自当前章节图片顺序。

## 测试要求

- 后端 API 返回同一项目内从 1 开始的 `project_image_no`。
- 不同项目的 `project_image_no` 均从 1 开始。
- 删除图片后，剩余图片的 `project_image_no` 和 `figure_label` 自动重排。
- 结果记录显示文本在图片删除或排序后刷新为最新图号。
- 保存章节后，内部 token 仍为 `[[FIG:全局图片ID]]`。
- 导出 DOCX 后题注和正文交叉引用显示最新 `图A-x-y`。
- DOCX 导入确认后仍能把临时 token 转为真实全局 ID token。

## 实施顺序建议

1. 扩展图片读取服务，为 API 响应补充项目内编号。
2. 扩展前端类型和显示组件，隐藏全局 ID，展示项目内编号和章节图号。
3. 强化结果记录显示层刷新逻辑，确保删除和排序后显示图号跟随最新图片列表。
4. 更新校验和导出测试，确认真实 token 不变、显示图号变化。
5. 更新 README 和相关实施文档。
