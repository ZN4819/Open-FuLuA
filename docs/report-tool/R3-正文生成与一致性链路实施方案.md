# R3：正文生成与一致性链路实施方案

> 状态：未实施。本文档为开发实施基线，不代表功能已交付。

## 1. 阶段定位

R3 在 R2 结构化数据域之上建立“确定性正文生成 + 人工覆盖 + 过期检测 + 结论可追溯”的一致性链路。它生成的是可审阅的 `report_blocks` 内容基线，不直接装配完整 DOCX；R0 已固化运行时模板及章节槽位，R4 负责把 R3 的有效块应用到权威 DOCX 模板。

本阶段的核心不是写出更像人的文字，而是确保同一份事实只维护一次，并让每段派生正文都能回答：来自哪些数据、用了哪条规则、何时生成、是否被人工改写、源数据变化后是否已过期。

复杂度：高。主要难点是附录 A 结果向问题/风险的确定性映射、稳定候选 ID、人工覆盖合并、级联过期、工作流闸门和正文之间的交叉一致性。

前置依赖：

- R0：已提供 `2023/2025-12-08` 运行时模板 manifest、章节键、块槽位和字段语义；R3 不自行解析或修改源 DOCX。
- R1：双项目、工作流、模板身份和导入/导出模式契约。
- R2：报告核心实体、中央对象库、章节和结构化块 API。
- 现有附录 A 权威评分服务：技术/管理评分、Ra/Rk 和打分表逻辑保持原样。

## 2. 经仓库验证的当前基线

- `backend/app/services/scoring.py` 已由后端权威计算技术与管理得分；Ra、Rk 属于内部技术评分参数。
- `assessment_rows` 和 `metric_results` 保存 A-1～A-8 的测评单元、对象、结果记录、D/A/K、符合情况和得分，但当前没有“问题候选”“风险候选”“总结结论”的派生实体。
- 当前 validator 会检查 A 行必填项、评分、图片和引用，并通过生成附录 A DOCX 做结构校验；不存在跨章节事实一致性校验。
- 当前结果记录模板是用户选择的符合性记录文本，不是正文自动生成规则，不能作为风险判定引擎。
- 当前 DOCX 生成器从空文档只生成附录 A。R3 不扩大该生成器；完整报告 DOCX 在 R4 由权威模板装配。
- R2 已为 `report_blocks` 预留生成基线、人工覆盖、源哈希和过期状态，可承载本阶段结果。

## 3. 统一契约继承与阶段专用状态

继续严格使用：

- `project_type=appendix_a|full_report`
- `workflow_status=draft|ready_for_review|confirmed`
- `template_edition=2023`、`template_revision=2025-12-08`
- `export_mode=draft|final`
- `import_mode=migration|roundtrip`
- Ra、Rk 不进入 Word
- Word 批注只产生 warning

R3 增加以下内部状态：

| 契约 | 合法值 | 含义 |
| --- | --- | --- |
| `generation_status` | `not_generated`、`current`、`stale`、`failed` | 当前基线是否与源数据一致 |
| `override_status` | `none`、`active`、`review_required` | 人工覆盖是否存在、源变化后是否需复核 |
| `candidate_status` | `candidate`、`confirmed`、`excluded`、`needs_input` | 问题/风险候选处理状态 |
| `generation_scope` | `section`、`downstream`、`all` | 生成范围 |

`workflow_status=confirmed` 不会自动把所有候选标记 confirmed；相反，进入项目 confirmed 前必须先满足候选和过期闸门。

## 4. 目标与非目标

### 4.1 目标

- 用版本化、确定性规则从结构化事实生成正文基线，相同输入必得相同结果。
- 实现“生成基线”和“人工覆盖”双层存储，人工编辑不破坏可重算基线。
- 计算源哈希并在事实变化时标记相关块过期，阻止旧结论被误当成最新结果。
- 建立可追溯链：`A结果 -> 问题候选 -> 风险候选 -> 总结/结论`。
- 提供候选确认、排除、补充依据和人工覆盖复核界面。
- 建立正文、附录 A、评分表和结论之间的一致性校验，为 R4 final DOCX 闸门提供结果。
- 完全禁止 AI、外部大模型和概率生成。

### 4.2 非目标

- 不装配完整 DOCX，不修改 R0 权威模板，不处理页眉页脚、目录、分页和 Word 样式；这些属于 R4。
- 不替代评估人员做风险确认；系统只生成可解释候选。
- 不从自由文本中用 NLP/AI 猜测问题和风险。
- 不改变附录 A 评分公式，不把 Ra/Rk 输出到正文块或 Word。
- 不支持任意用户自定义可执行规则；第一版规则随应用版本交付并通过代码审查。
- 不允许人工覆盖掩盖源数据已变化的事实。

## 5. 一致性模型

### 5.1 生成基线、人工覆盖与有效内容

每个 `source_kind=generated` 的 `report_block` 使用以下字段：

- `baseline_json`：规则引擎最新生成的完整结构化内容。
- `baseline_hash`：规范化 baseline 的 SHA-256。
- `source_snapshot_json`：生成所使用的最小事实快照，不保存无关敏感字段。
- `source_hash`：规范化源快照的 SHA-256。
- `rule_set_id`：例如 `report-content-2023-2025-12-08-v1`。
- `rule_id`：具体规则稳定标识。
- `override_json`：只保存人工改变的字段和审阅说明，不复制整份 baseline。
- `generation_status`、`override_status`。
- `generated_at`、`generated_by_version`、`reviewed_at`。

有效内容按确定性顺序计算：

```text
effective_content = apply_allowed_override(baseline_json, override_json)
```

覆盖 allowlist 由块类型定义。例如问题候选允许改写“问题描述、补充依据、处置状态”，不允许改写源 A 行 UUID、原始符合情况和规则 ID。任何 API 都不得直接把人工内容写回 `baseline_json`。

### 5.2 源哈希与过期传播

源快照采用稳定 JSON 序列化：键排序、Unicode NFC、日期 ISO、Decimal 固定位数、集合按稳定 UUID 排序、忽略更新时间等非业务字段。

当以下事实变化时触发影响分析：

- A 行的测评单元、对象绑定、结果记录、D/A/K、符合情况、对象分、单元分。
- 中央对象名称、类型、子系统、关系或停用状态。
- 报告元数据、组织、成员、系统画像中的被规则引用字段。
- 问题候选的确认/排除和人工补充。
- 风险候选的确认/排除、等级和处置说明。

依赖图固定为有向无环图：

```text
A行/对象/系统事实
  -> 问题候选
  -> 风险候选
  -> 测评结果总结
  -> 总体结论与建议
```

源变化时只标记下游 `stale`，不立即覆盖 baseline 和 override。用户执行重新生成后写入新 baseline；若存在 override 且受影响字段对应的基线发生变化，设置 `override_status=review_required`，必须人工确认保留、调整或清除覆盖。

### 5.3 稳定候选标识

问题候选 ID 由以下稳定键生成，不使用当前排序号：

```text
finding:<assessment_row_uuid>:<rule_id>
```

风险候选 ID：

```text
risk:<finding_candidate_id>:<risk_rule_id>:<affected_object_uuid-or-none>
```

报告块 `block_key` 使用上述稳定键。A 行删除后对应候选不物理删除，标记 source missing/stale，等待用户确认排除；这样保留审阅轨迹。

## 6. 确定性规则架构

### 6.1 规则资产

规则资产放入独立版本目录，例如：

```text
templates/report/2023/2025-12-08/rules/
  content_rules.json
  finding_rules.json
  risk_rules.json
  conclusion_rules.json
  schemas/*.json
```

规则文件随应用只读发布，具有：`rule_set_id`、模板身份、schema 版本、规则优先级、输入字段 allowlist、条件、固定文案模板、输出 block schema 和测试向量。启动时校验文件哈希和 schema；规则冲突、未知字段或重复 ID 使该规则集不可用，不静默跳过。

规则执行器只支持有限表达式：等值、集合包含、数值比较、all/any、空值判断和固定格式化。禁止 `eval`、脚本、正则替换执行、网络调用和动态模块加载。

### 6.2 普通正文基线

基础信息章节从 `report_metadata`、组织、成员、系统画像、对象和关系生成段落/表格块。每个块的规则必须声明字段来源，例如系统名称只能来自 `system_profiles.system_name`，不得从章节自由文本回读。

固定文案采用参数化句式和明确缺失行为：

- 必填字段缺失：块状态 `failed`，返回字段级错误。
- 可选字段缺失：按规则省略对应句段，不输出“暂无”等未经模板允许的占位语。
- 列表为空：生成空状态但标记章节 incomplete；是否允许 final 由 manifest 决定。
- 多对象：按 manifest 指定的类型和 sort_order 排序，不按数据库自增 ID。

### 6.3 A 结果到问题候选

规则输入只使用已保存且后端重算后的 A 数据：

- 技术章节：D/A/K 状态、对象分/单元分、结果记录、测评单元和对象 UUID。
- 管理章节：符合情况、单元分、结果记录、固定对象。

候选触发规则必须显式配置。例如技术项存在 `×`、管理项为“不符合/部分符合”、或规则声明的得分阈值时生成候选；“不适用”和全部 `/` 不自动生成问题。具体阈值以经确认的规则资产为准，不能在代码中凭经验补充。

候选 baseline 至少包含：来源 A 行 UUID/章节/单元/对象、触发事实、问题类别、固定描述模板、证据引用、建议核验项、rule_id。Ra/Rk 可在评分服务内部参与对象分计算，但候选快照、文案、块 payload 和 R4 Word 上下文不得包含 Ra/Rk 原值。

若 A 行未完成、分数非法或对象未绑定但规则要求对象类型，则候选状态为 `needs_input`，不猜测结论。

### 6.4 问题候选到风险候选

风险规则使用已确认问题、受影响对象类型/关系、业务影响配置和固定风险矩阵。风险等级必须由离散矩阵确定，例如可能性档位 × 影响档位映射；矩阵和每个档位输入要求写入 `risk_rules.json`。

无法确定可能性或影响时生成 `needs_input`，要求评估人员选择并补充依据。排除的问题不生成活动风险；问题重新启用时原稳定风险块恢复为 stale，不创建重复项。

风险 baseline 至少包含：来源问题 ID、受影响对象、风险场景模板、可能性、影响、等级、已有控制、建议措施、rule_id。人工可调整等级，但必须填写调整理由，保存为 override，不能修改 baseline 矩阵结果。

### 6.5 风险到总结和结论

总结和结论只读取：

- 后端权威的章节/层面/总评分及适用性结果。
- confirmed 的问题和风险。
- excluded 数量及理由摘要（不输出内部审阅备注）。
- 各风险等级计数、涉及对象/章节分布。
- 模板 manifest 允许的系统与组织事实。

结论使用固定决策表和参数化文案，不使用自由生成。若存在 stale、needs_input、未审阅 override、评分未完成或决策表无法匹配，则结论块 `failed/stale`，不得沿用旧结论。

风险分析摘要中的高风险判定是同一快照的确定性派生值：confirmed 且活动的高风险项数量大于 0 时写入“判定系统存在高风险”，数量等于 0 时写入“判定系统不存在高风险”。未完成分析、`needs_input`、stale 或未审阅 override 均不得被视为 0 项，必须阻止该摘要和正式报告生成。

总结中的数字、问题清单、风险清单和结论使用同一生成运行的只读快照，防止生成过程中数据变化导致前后不一致。

## 7. 生成运行与事务契约

一次生成建立 `generation_run_id`（可作为 report_blocks 的批次字段或独立轻量运行表），记录 project UUID、scope、规则集、开始/结束时间、输入总哈希、状态和错误摘要。

流程：

1. 以只读事务读取项目、A 行、评分和 R2 实体，形成一致快照。
2. 校验项目类型、模板身份和规则资产。
3. 构建依赖图并计算目标块。
4. 在内存中完成全部 schema 校验和哈希。
5. 在单写事务中按稳定 block_key upsert baseline；保留 override；更新过期/复核状态。
6. 若项目原状态为 ready_for_review 或 confirmed，内容变化后回退 draft。
7. 返回生成摘要和所有失败项。

一个 scope 内出现任一系统错误时不提交部分新 baseline。业务缺失项可以作为 `failed/needs_input` 结果整体提交，便于用户逐项处理，但响应必须区分“运行失败”和“业务未完成”。

## 8. API 契约

### 8.1 生成与影响预览

- `POST /api/projects/{uuid}/report/generation/impact-preview`
- `POST /api/projects/{uuid}/report/generation/runs`
- `GET /api/projects/{uuid}/report/generation/runs/{run_id}`

生成请求：

```json
{
  "scope": "downstream",
  "section_keys": ["assessment.findings"],
  "expected_project_revision": 18
}
```

impact-preview 返回会重算的块、会变 stale 的下游块、存在人工覆盖的块和预计阻断项，不写数据库。

项目 revision 已变化返回 409；规则集不可用返回 503 `RULE_SET_UNAVAILABLE`；业务缺失返回成功运行摘要并列出 `needs_input`，不得返回伪造正文。

### 8.2 候选审阅

- `GET /api/projects/{uuid}/report/findings?status=...`
- `PUT /api/projects/{uuid}/report/findings/{block_uuid}/decision`
- `GET /api/projects/{uuid}/report/risks?status=...`
- `PUT /api/projects/{uuid}/report/risks/{block_uuid}/decision`

decision 接受 `confirmed|excluded|needs_input` 允许的转换、补充依据和 expected revision。excluded 必须填写理由；调整风险等级必须填写 override reason。

### 8.3 人工覆盖

- `PUT /api/projects/{uuid}/report/blocks/{block_uuid}/override`
- `DELETE /api/projects/{uuid}/report/blocks/{block_uuid}/override`
- `POST /api/projects/{uuid}/report/blocks/{block_uuid}/override-review`

更新只接受该 block schema 的覆盖 allowlist。override-review 接受 `keep|update|discard`；keep 必须记录复核说明并把 review_required 转为 active。

### 8.4 一致性校验

- `POST /api/projects/{uuid}/report/consistency-checks`
- `GET /api/projects/{uuid}/report/consistency-checks/latest`

响应按 error/warning/info 分类，至少包含 source/target block、规则 ID、当前值和期望关系。批注问题固定 warning。R3 不提供完整报告 DOCX 导出端点；R4 的 `export_mode=draft|final` 必须消费此校验结果。

### 8.5 导入模式影响

- `migration` 导入的数据初始视为人工事实，派生块统一 `not_generated`，必须运行 R3 后才能进入 ready_for_review。
- `roundtrip` 只能更新 R4 标记为可回填的人工字段或 override，不接受对 baseline、source_hash、规则 ID、A 权威评分的修改。
- roundtrip 文档中的批注形成 warning 列表，不自动变成 override、问题或风险。

## 9. UI 契约

### 9.1 生成控制

- 章节页显示“未生成 / 最新 / 已过期 / 生成失败”，并显示来源更新时间和规则集版本。
- “重新生成”先打开影响预览，明确哪些人工覆盖需要复核；用户确认后执行。
- 生成失败保留旧 baseline 但标记 stale/failed，不把旧内容展示成最新。
- 禁止提供“AI润色”“自动写作”等入口，也不以隐藏网络服务实现。

### 9.2 基线与覆盖对比

- generated 块默认展示有效内容，并可切换查看“系统基线 / 人工覆盖 / 来源事实”。
- 人工编辑只产生 override；UI 明示哪些字段不可改及其来源。
- 源变化后用差异视图展示旧 baseline、新 baseline 和 override，要求 `keep/update/discard`。
- 清除覆盖后立即回到当前 baseline，不删除审阅日志。

### 9.3 问题与风险审阅台

- 按 candidate/confirmed/excluded/needs_input 过滤。
- 每项显示来源 A 章节、测评单元、对象、触发事实、证据、规则 ID和下游引用。
- 用户确认或排除问题后，风险和总结节点立即标记 stale，但不自动在后台悄悄重算。
- 风险等级人工调整必须填写理由；保留矩阵基线供对照。

### 9.4 总结与结论

- 结论页同时显示评分摘要、问题/风险计数、未处理项和一致性问题。
- 存在 stale/needs_input/review_required 时禁止把项目置为 ready_for_review 或 confirmed，并提供可导航清单。
- 批注 warning 单独显示，不因其存在禁用状态按钮。

## 10. 一致性校验规则

至少实现：

- 每个活动问题候选能追溯到存在的 A 行和规则。
- confirmed 风险必须追溯到 confirmed 问题；excluded 问题不得出现在有效风险/总结中。
- 总结的技术/管理符合数量与同一评分快照一致。
- 总结和结论的问题、风险数量及等级分布与有效候选一致。
- 报告中显示的系统名、组织名、对象名与权威实体一致；允许的历史快照必须明确标记。
- 所有 generated 块 `source_hash` 与当前源快照匹配。
- 所有 active override 在源变化后已复核。
- final 消费上下文中不存在 Ra/Rk 键或文本；扫描包括块 payload、source snapshot 和预留导出 DTO。
- 批注仅 warning；不得被“warning 数大于零”误判为 error。

## 11. 可提交工作包

### WP-R3.1：规则资产 schema 与安全执行器

**输入**：R0 manifest、模板身份、经业务确认的正文/问题/风险/结论规则表。

**具体改动**：定义版本化 JSON Schema、有限表达式解释器、规则加载/哈希/冲突检测和测试向量；明确禁止 AI、网络和 eval。

**失败行为**：规则重复、未知字段、schema 错误或哈希不匹配时整个规则集不可用，返回稳定诊断；不跳过错误规则继续生成。

**测试**：合法规则、重复 ID、未知操作符、字段越权、恶意表达式、确定性排序、同输入同输出、不同 locale/时区一致。

**验收**：规则执行不访问网络、不执行动态代码；规则集版本与模板身份一一匹配。

**建议提交**：`R3.1: 建立确定性正文规则与安全执行器`

**失败行为**：非法覆盖不写入；哈希计算或 schema 校验失败时保留旧块并把运行标记 failed；源变化不自动覆盖人工内容。

**测试**：规范化哈希、字段顺序/Unicode/Decimal、覆盖合并、清除覆盖、源变化、级联 stale、复核三种决策、并发冲突。

**验收**：任意生成块可同时查看基线、覆盖、有效值和源；过期状态可重复计算。

**建议提交**：`R3.2: 实现生成基线人工覆盖与过期检测`

### WP-R3.3：普通章节确定性正文

**输入**：metadata、组织、成员、system profile、对象/关系和 content_rules。

**失败行为**：必填事实缺失产生字段级 failed；可选事实按规则省略；禁止生成模糊兜底文本。

**测试**：单/多组织、空列表、对象排序、特殊字符、同名对象、跨项目隔离、固定黄金 JSON。

**验收**：相同结构化输入在重复生成后 baseline 和 hash 完全一致。

**失败行为**：未完成评分、规则缺字段或对象要求不满足时 needs_input，不猜问题；规则执行系统错误时整批不提交。

## 12. 迁移与回滚

- R2 已存在的 manual/template_default 块不自动改成 generated。R3 初始化只为 manifest 声明的 generated 槽位补充块。
- 首次生成前所有派生块为 `not_generated`，不从已有自由文本猜测 baseline。
- 若项目已有人工正文，可由 migration 向导选择保留为 manual block 或生成块 override；必须预览，不能覆盖。
- 规则集升级不自动重算 confirmed 项目。启动时标记“可用新规则集”，用户先看影响预览；选择升级后相关块 stale 并回退 draft。
- 回滚应用版本使用升级前数据库备份；规则资产与代码版本共同回滚。禁止新代码生成的 baseline 由旧规则解释。
- 单次失败生成不需数据库回滚到备份：事务保证旧 baseline 保留，generation run 记录失败原因。

## 13. 风险与安全

- **自动化越权替代专业判断**：输出始终是候选；问题/风险需人工确认，needs_input 不自动填值。
- **不确定文本生成**：完全禁用 AI、LLM、联网补全和概率模型；所有文案来自版本化固定规则。
- **规则注入**：规则只读随包发布，有限解释器无 eval；启动校验 schema 和哈希。
- **旧结论误用**：源哈希、依赖图和 stale 闸门；失败时不得展示为最新。
- **人工覆盖丢失**：baseline/override 分层；重算保留覆盖并要求复核。
- **循环依赖**：依赖图固定 DAG，规则资产加载时检测循环。
- **并发快照不一致**：生成先读一致快照，写入前检查项目 revision。
- **敏感数据扩大复制**：source snapshot 只保存规则实际字段；日志只记录 UUID、规则 ID 和摘要。
- **Ra/Rk 泄漏**：规则输入 DTO 不含 Ra/Rk，只接收评分服务派生结果；扫描 baseline、override、快照和 R4 DTO。
- **批注误处理**：批注仅 warning，不自动形成问题、风险或人工覆盖，也不因数量阻断 final。
- **roundtrip 篡改**：只导入允许的人工字段/override，工具标识、项目 UUID、模板版本和 revision 全部校验。

## 14. 阶段验收闸门

- 所有规则资产通过 schema、冲突、哈希、安全操作符和黄金向量测试。
- 同一输入、规则集和模板身份在重复运行、不同机器及时区下产生相同 baseline/hash。
- baseline、override、effective content 和 source snapshot 可独立审计；重算不丢人工覆盖。
- A 结果到问题、问题到风险、风险到总结结论全链路有稳定 ID 和来源追踪。
- stale、needs_input、review_required、failed 任一存在时不能进入 ready_for_review/confirmed；批注 warning 除外。
- 总结与结论使用同一生成快照，数字与 confirmed 问题/风险及权威评分一致。
- `migration|roundtrip` 行为明确，roundtrip 不能修改基线、规则 ID、评分和哈希。
- 代码、UI、日志和网络测试证明没有 AI/LLM 调用。
- Ra/Rk 在 report_blocks、source snapshot、R4 DTO 和未来 Word 上下文中为零泄漏。
- 现有附录 A 保存、评分、DOCX、XLSX、导入、校验和预览回归通过。
- R4 可通过稳定 API 获取 `draft|final` 装配上下文；R3 本身不直接生成完整 DOCX。
