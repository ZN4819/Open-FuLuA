# R1：双项目模式与兼容迁移实施方案

> 状态：技术实施与本地验收已完成，待本阶段 Pull Request 合入 `main`。完整报告正文数据域仍从 R2 开始实施。

## 1. 阶段定位

R1 是“附录 A 编写工具”升级为“完整报告生成工具”的兼容底座阶段。本阶段严格只处理项目身份、工作流状态存储、不可变模板包绑定和附录 A 复制升级，不开发报告正文编辑器，不落地总方案第 3.6 节的报告业务字段、关联或派生规则，也不改变现有附录 A、评分、DOCX 和 XLSX 的业务结果。同一客户端可以同时、安全地承载两种项目：

- `appendix_a`：现有附录 A 项目，行为与当前版本保持一致。
- `full_report`：完整报告项目，绑定明确且已通过 R0 冻结的报告模板包，并为 R2 预留初始化标记，不预建报告业务数据。

本阶段必须解决四个根问题：项目缺少跨数据库稳定标识；旧项目没有类型；报告工作流没有状态；从附录 A 升级完整报告时不能污染源项目。

复杂度：中高。主要风险不在字段增加，而在 SQLite 幂等迁移、旧客户端数据兼容、图片文件复制、导入导出契约兼容和失败回滚。

前置依赖：R0 已固化统一枚举、模板身份和资源包契约；同时依赖现有数据库备份/恢复、项目删除清理、附录 A 项目复制所需的数据访问能力。后续 R2、R3 必须依赖本阶段稳定契约。

## 2. 经仓库验证的当前基线

- 后端与桌面端当前 schema 版本均为 `3`：`backend/app/runtime.py` 与 `desktop/src/main.ts`。
- `projects` 目前只有自增 `id`、`name`、`created_at`、`updated_at`，没有 UUID、项目类型、工作流状态和模板版本。
- `database.create_project()` 创建项目后固定写入 `SECTION_SEED` 的 A-1～A-8；现有 API 的 `ProjectCreate` 只有名称。
- 附录 A 数据分散在 `appendix_sections`、`section_subsystems`、`assessment_rows`、`metric_results`、`evidence_images`、`cross_references`；图片文件位于项目级存储目录。
- DOCX 生成从空文档创建附录 A，并强校验 8 个分节、8 张表；XLSX 评分表同样以现有附录 A 数据为权威来源。
- DOCX 导入任务最终创建的仍是普通附录 A 项目；当前导入没有 `migration|roundtrip` 模式概念。
- 客户端已有升级前备份、schema 版本闸门、恢复窗口和项目运行文件清理能力，可作为迁移安全网。

## 3. 统一契约

本阶段建立并由后续阶段沿用以下枚举，数据库、Pydantic、TypeScript 和测试夹具必须同源：

| 契约 | 合法值 | 说明 |
| --- | --- | --- |
| `project_type` | `appendix_a`、`full_report` | 项目能力边界，不允许客户端任意字符串 |
| `workflow_status` | `draft`、`ready_for_review`、`confirmed` | `confirmed` 只表示结构化数据已确认，不等同于文件已签章 |
| 模板版本 | `template_edition=2023`、`template_revision=2025-12-08` | 完整报告项目必填；附录 A 项目允许为空 |
| 导出模式 | `draft`、`final` | R4 的完整报告接口只接受这两个值；现有附录 A `editable|final` 接口在 R1 保持不变 |
| 导入模式 | `migration`、`roundtrip` | `migration` 用于外部/历史文档迁入；`roundtrip` 只接收本工具可识别的导出物 |

全局约束：Ra、Rk 继续参与内部评分和 XLSX，但不得写入任何 Word 正文、附录或隐藏内容控件；Word 批注的存在只产生警告，不单独阻止保存、确认或导出。

### 3.1 R0 冻结输入与第 3.6 节承接边界

R1 必须以 R0 冻结记录为启动前置：`package_id=report-2023-2025.12.08`、edition/revision、六项受信资产哈希和注册表校验结果必须一致。R1 只把这一身份绑定到新建或复制升级的 `full_report` 项目，不解析字段字典为项目业务表。

| 总方案业务基线 | R1 必须保证 | R1 明确不做 |
| --- | --- | --- |
| 3.6.1 报告身份、单位和版本 | 为 R2 预留稳定项目 UUID；不可变绑定模板包；保留后续导出版本元数据的契约名 | 不录入报告编号、系统名称、单位或版本，不组装文件名 |
| 3.6.2 日期、人员和分发 | 只提供项目身份与 `draft` 状态 | 不创建阶段日期、人员、附录 B 或分发数据 |
| 3.6.3 基本信息、标准和密码产品 | 复制升级时保留现有附录 A 原始数据 | 不创建基本信息表、产品表、标准或特殊指标 |
| 3.6.4 附录 A、测评对象和章节投影 | 复制附录 A 时精确重映射行、图片和交叉引用 ID | 不建中央对象库，不生成表 3-4～4-11 投影 |
| 3.6.5 指标结论、结果修正和最终投影 | 保证复制前后现有评分语义一致 | 不建结果修正关系，不计算原始/最终投影 |
| 3.6.6 统计、风险、结论和正文 | 不得破坏现有附录 A 权威评分 | 不生成任何统计、风险、结论、正文或过期状态 |

任一超出上表的报告字段、关联、校验或生成逻辑出现在 R1 PR 中，都应视为阶段边界失败，拆回 R2/R3/R4 后才能合并。

## 4. 目标与非目标

### 4.1 目标

- 为每个项目生成不可变、全局唯一的 `project_uuid`，数据库复制或导出后仍可识别来源。
- 旧项目升级后幂等标记为 `appendix_a`，数据、图片、评分和现有导出结果不变。
- 支持直接创建 `full_report`，初始化项目身份、`draft` 工作流状态、不可变模板包绑定和现有附录 A 子域。
- 支持把一个 `appendix_a` 项目“复制升级”为新的 `full_report`；源项目及源图片保持不变。
- API 和前端根据项目类型做能力路由，不以“是否存在某张表”猜测类型。
- 明确导入、导出模式的兼容映射和错误响应。

### 4.2 非目标

- 不实现报告元数据、组织成员、系统画像等正文数据域；由 R2 实现。
- 不保存 `system_name`、`report_number`、委托/被测单位、日期、人员、分发份数、密码产品/算法、标准、特殊指标或任何第 3～7 章关联数据；项目 `name` 只是客户端列表标题，不是报告系统名称。
- 不生成完整报告正文；确定性正文由 R3 实现，权威运行时模板由 R0 产出，完整 DOCX 装配由 R4 实现。
- 不允许 `full_report` 项目在 R2 完整性校验就绪前进入 `ready_for_review` 或 `confirmed`；R1 只固化状态枚举和后续状态机接口。
- 不把现有项目就地转换为完整报告，不删除或隐藏附录 A 项目。
- 不承诺导入任意 DOCX；当前附录 A 导入仍按原有规则工作。
- 不改变现有评分算法、固定测评对象、XLSX 模板和 Ra/Rk 规则。

## 5. 架构与数据契约

### 5.1 `projects` 扩展

建议 schema 版本提升为 `4`，在 `projects` 增加：

| 字段 | 类型 | 约束/默认值 |
| --- | --- | --- |
| `project_uuid` | TEXT | 非空、唯一；新建使用 UUIDv4，生成后不可修改 |
| `project_type` | TEXT | 非空，旧记录和兼容创建默认 `appendix_a` |
| `workflow_status` | TEXT | 非空，默认 `draft` |
| `template_package_id` | TEXT | `full_report` 固定绑定 `report-2023-2025.12.08`；`appendix_a` 为 NULL |
| `template_edition` | TEXT | `full_report` 固定 `2023`；`appendix_a` 为 NULL |
| `template_revision` | TEXT | `full_report` 固定 `2025-12-08`；`appendix_a` 为 NULL |
| `template_asset_set_hash` | TEXT | `full_report` 创建时记录 R0 冻结资产集指纹，后续不可修改 |
| `source_project_uuid` | TEXT | 复制升级时记录源项目 UUID，否则 NULL |
| `created_by_operation` | TEXT | `create`、`migration_import`、`roundtrip_import`、`upgrade_copy` |

SQLite 旧表增加列后再建立 `project_uuid` 唯一索引。迁移代码不得用一次性随机批量 SQL；应逐行读取主键，以 UUIDv5（命名空间由应用固定，名称包含数据库实例标识和旧 project id）或持久化 UUIDv4 回写，事务重试时必须读取已有值，保证幂等。数据库实例标识可新增单行 `app_metadata` 表保存，避免复制数据库后再次迁移产生不同 UUID。

应用层和数据库层都校验枚举及组合约束：

- `full_report` 必须具有上述固定 package ID、edition、revision 和资产集指纹；创建前必须通过 R0 registry 完整性校验，绑定后禁止 `PUT/PATCH` 修改。
- `appendix_a` 的模板包身份必须全部为空；读取历史异常数据时返回明确诊断，不静默修复。
- R1 中新建或复制升级的 `full_report` 始终为 `draft`；`ready_for_review` 和 `confirmed` 的枚举可持久化，但状态迁移必须在 R2 完整性校验接入后才开放。客户端不能直接写任意状态。

### 5.2 服务边界

新增项目应用服务，不让 API 直接拼接多表 SQL：

- `create_project(command)`：创建指定类型并调用类型初始化器。
- `initialize_appendix_a(project_id)`：保留现有 A-1～A-8 初始化逻辑。
- `initialize_full_report(project_id, template_binding)`：R1 只验证并写入不可变模板包绑定、A 子域和“待 R2 初始化”标记；R2 接管具体报告实体。
- `clone_appendix_a_domain(source_id, target_id)`：事务内复制结构化数据，事务外分阶段复制文件，并支持补偿清理。
- `upgrade_project_copy(source_uuid, idempotency_key)`：只允许 `appendix_a -> full_report`，返回新项目。
- `transition_workflow(project_uuid, target_status)`：集中处理状态机与确认前校验钩子；R1 中对 `ready_for_review|confirmed` 返回 409 `REPORT_VALIDATION_NOT_AVAILABLE`，直到 R2 注册完整校验器。

升级复制必须建立行 ID 映射：section、row、image。`cross_references.source_row_id` 和 `target_image_id` 使用新 ID 重写，`[[FIG:旧ID]]` token 同步改为新图片 ID。不得硬链接源图片；目标目录使用物理副本，避免删除任一项目影响另一项目。

### 5.3 API 契约

#### 创建项目

`POST /api/projects`

```json
{
  "name": "某系统密评报告",
  "project_type": "full_report",
  "template_package_id": "report-2023-2025.12.08",
  "template_edition": "2023",
  "template_revision": "2025-12-08"
}
```

兼容规则：旧客户端只发送 `name` 时创建 `appendix_a`。创建 `full_report` 时模板字段缺失、不匹配、未冻结或 registry/哈希校验失败时，不创建项目，并返回 HTTP 422/503 及稳定错误码 `UNSUPPORTED_TEMPLATE_IDENTITY|TEMPLATE_PACKAGE_UNTRUSTED`。资产集指纹由服务端 registry 写入，不接受客户端提交。

项目读取响应新增全部身份字段；内部数值 `id` 继续用于当前接口兼容，新接口和跨项目操作优先使用 UUID。

#### 复制升级

`POST /api/projects/{project_uuid}/upgrade-copy`

```json
{
  "name": "某系统密评报告",
  "template_package_id": "report-2023-2025.12.08",
  "template_edition": "2023",
  "template_revision": "2025-12-08",
  "idempotency_key": "客户端生成的UUID"
}
```

成功返回 HTTP 201 和新项目；同一源项目与幂等键重复请求返回同一结果。源类型不是 `appendix_a` 返回 409 `PROJECT_TYPE_NOT_UPGRADABLE`。复制任何一步失败时返回结构化错误并删除未完成目标记录和目标文件，不修改源项目。

#### 工作流

- `POST /api/projects/{project_uuid}/workflow/ready-for-review`
- `POST /api/projects/{project_uuid}/workflow/confirm`
- `POST /api/projects/{project_uuid}/workflow/reopen`

三个端点及状态机契约可在 R1 固化，但 R1 未具备第 3.6 节完整性校验，因此 `ready-for-review` 和 `confirm` 必须返回 409 `REPORT_VALIDATION_NOT_AVAILABLE`，不得只检查项目身份就进入后续状态。`reopen` 对已有历史状态的项目可回退到 `draft`，并记录操作时间。

#### 导入导出兼容

- R1 只在共享契约中预留完整报告的 `draft|final` 和 `migration|roundtrip` 枚举，不提前开放完整报告导入导出接口。
- 现有附录 A `/exports/docx?mode=editable|final` 及 `/api/imports/docx` 行为保持不变，避免在 R4、R6、R7 之前改变已经交付的接口语义。
- R4 实现完整报告 `draft|final`；R6、R7 分别实现 `migration` 和 `roundtrip`，不得复用现有附录 A 导入入口后静默改变其用途。

所有错误响应至少包含 `code`、`message`、`project_uuid`（可获得时）、`field` 和 `details`，禁止仅返回 Python 异常文本。

### 5.4 UI 契约

- 新建项目对话框提供“仅编写附录 A”和“生成完整报告”两个清晰选项，不暴露数据库术语。
- 项目卡片显示类型、工作流状态和完整报告模板版本。
- `appendix_a` 项目保留现有打开流程，并提供“复制为完整报告”操作；确认对话框明确“将创建新项目，源项目不会改变”。
- `full_report` 项目在 R1 暂进入占位工作台，附录 A 入口可用，正文入口显示“将在下一阶段提供”，不得假装功能已完成。
- 前端路由和能力判断只读取 `project_type`，不根据项目名称或 section 数量推断。
- 批注警告在 R1 仅作为导入预览信息显示，不作为红色阻断错误。

## 6. 可提交工作包

### WP-R1.1：共享契约与 schema 迁移

**输入**：schema 3 数据库、现有 `projects` 表、统一枚举、R0 最终冻结记录和受信模板 registry。

**具体改动**：新增 Python/TypeScript 契约；实现 schema 4 迁移、数据库实例标识、项目 UUID 回填、模板包绑定列、组合约束校验；同步桌面端目标 schema。

**失败行为**：迁移任一 SQL 或 UUID 回填失败时整个事务回滚，保留 schema 3；启动器进入现有恢复流程，不允许后端以半迁移数据库运行。

**测试**：空库初始化；真实 schema 3 夹具升级；重复执行幂等；UUID 唯一；旧项目字段值；旧项目模板绑定全空；full_report 绑定四元组合法/非法；高版本数据库拒绝；迁移失败回滚。

**验收**：同一份旧数据库迁移两次结果一致，所有旧项目均为 `appendix_a/draft`，附录 A 行数、评分和图片校验和不变。

**建议提交**：`R1.1: 增加双项目身份契约与幂等迁移`

### WP-R1.2：类型化创建与项目读取

**输入**：R1.1 schema、新旧项目创建请求。

**具体改动**：重构项目应用服务；兼容旧请求；实现 full_report 身份、`draft` 状态和不可变模板包绑定初始化；扩展项目列表和详情 schema，不创建 R2 实体。

**失败行为**：模板包未冻结、身份不支持或哈希不可信时不创建任何项目；A 子域初始化失败时回滚项目主记录；禁止用当前最新模板自动替换请求的 package ID。

**测试**：旧请求创建 appendix_a；显式创建两类项目；非法类型/状态/模板组合；响应字段和 API 向后兼容。

**验收**：现有前端不改请求也能创建并打开附录 A；新 API 可创建模板身份固定的完整项目。

**建议提交**：`R1.2: 支持附录A与完整报告项目初始化`

### WP-R1.3：复制升级服务

**输入**：有多章节、子系统、图片和交叉引用的附录 A 项目。

**具体改动**：实现多表复制、ID/token 重映射、目标文件复制、幂等操作记录和失败补偿；禁止就地升级。

**失败行为**：数据库失败回滚；文件失败清理目标文件和目标项目；源记录、源文件和更新时间均不得变化。若补偿清理失败，记录可诊断日志并把目标标记为不可打开的失败操作，不返回成功。

**测试**：空项目、完整项目、多图片引用、同题注多图、重复幂等键、不同幂等键、磁盘复制故障、目标清理、源哈希不变。

**验收**：新完整项目的附录 A 导出 DOCX/XLSX与源项目语义一致；删除新项目后源项目仍可正常导出。

**建议提交**：`R1.3: 实现附录A复制升级且保护源项目`

### WP-R1.4：工作流与后续导入导出契约预留

**输入**：类型化项目、现有 DOCX 导入和导出接口。

**具体改动**：固化状态机契约和能力检查，R1 仅允许保持/回到 `draft`；在共享类型中预留 `draft|final` 和 `migration|roundtrip`；保持现有附录 A 导入导出接口不变；为后续阶段定义稳定错误码。批注问题继续只作为 warning。

**失败行为**：`ready_for_review|confirmed` 迁移固定返回 409 `REPORT_VALIDATION_NOT_AVAILABLE`；R1 对完整报告导入导出能力请求返回明确的“阶段能力未提供”，不得回退调用附录 A 生成器或导入器。

**测试**：`draft` 保持/回退和后续状态阻断；现有 editable/final 调用和附录 A 导入回归；预留枚举的 Python/TypeScript 一致性；批注 warning；Ra/Rk 不出现在 Word XML。

**验收**：旧 DOCX 导入导出回归通过且响应语义不变；后续能力探测有稳定错误码；Ra/Rk 的 Word 零泄漏扫描通过。

**建议提交**：`R1.4: 统一工作流及导入导出模式契约`

### WP-R1.5：双项目首页与升级交互

**输入**：扩展后的项目 API。

**具体改动**：新建类型选择、项目卡片标签、升级确认和 full_report 占位工作台；按类型路由；保留现有附录 A 工作台行为。

**失败行为**：网络或复制失败时保留当前项目与输入，显示服务端结构化原因；不得乐观隐藏源项目或跳入未创建项目。

**测试**：新旧创建、类型标签、升级确认/取消/失败/成功、刷新后状态、键盘与窄屏可用性。

**验收**：用户可同时管理两类项目，并能明确辨认“复制升级”不会改变源项目。

**建议提交**：`R1.5: 完成双项目入口与复制升级交互`

### WP-R1.6：阶段回归与桌面迁移验收

**输入**：R1 全部实现、schema 3 样本数据库、安装版测试环境。

**具体改动**：补充升级备份/恢复验收、项目复制端到端测试和文档；不增加业务功能。

**验收**：阶段验收闸门全部满足。

**建议提交**：`R1.6: 完成双项目兼容迁移验收`

## 7. 迁移与回滚

1. 桌面启动器按现有机制先创建数据库备份，再启动 schema 4 后端。
2. schema 迁移在单一 `BEGIN IMMEDIATE` 事务完成；文件系统不参与 schema 迁移。
3. 迁移后执行只读审计：项目数、A章节数、行数、图片数、引用数、评分摘要和 UUID 唯一性。
4. 对每个 `full_report` 额外审计 package ID、edition、revision 和资产集指纹；必须与 R0 冻结 registry 一致，禁止自动切换到“最新”模板。
5. 审计失败则终止启动并提示恢复备份，不能自动删除用户数据重建。
6. 从 schema 4 回退到旧客户端不受支持；回滚方式是卸载新版本并恢复升级前 schema 3 备份。
7. 复制升级是新增操作，不需要数据库降级。失败目标由补偿流程清理；源项目永不作为补偿对象。
8. 已绑定模板包不可通过普通回滚或数据修复原位改写；后续模板更换必须另行提供带预览、确认和备份的显式迁移。

## 8. 风险与安全

- **UUID 冲突或漂移**：数据库唯一索引；已生成 UUID 永不重算；复制数据库不会触发重新赋值。
- **路径穿越/覆盖源文件**：所有复制目标必须经 storage 根目录约束和新项目目录计算；禁止接受客户端路径。
- **磁盘空间不足**：复制前估算图片总量与可用空间，失败时补偿清理。
- **重复请求生成多个副本**：服务端持久化幂等键，不依赖前端按钮禁用。
- **状态绕过**：工作流由后端状态机控制，客户端字段不可直接更新。
- **模板身份伪造**：完整项目只接受内置 allowlist 的 edition/revision。
- **兼容回归**：旧接口保留，废弃映射记录日志但不改变返回文件语义。
- **Word 数据泄漏**：测试扫描 `word/document.xml`、页眉页脚、批注、自定义 XML，确保 Ra/Rk 不出现。
- **批注规则**：检测到批注仅发 warning；批注文本仍按本地敏感数据处理，不写入普通日志。

## 9. 阶段验收闸门

R1 只有同时满足以下条件才可合并：

- schema 3 到 schema 4 迁移、重复启动和失败恢复均通过。
- 所有旧项目被幂等标记为 `appendix_a`，且结构化数据、图片和导出结果无语义变化。
- 直接创建 `full_report` 后模板身份固定为 `2023/2025-12-08`。
- 直接创建和复制升级项目都不可变绑定 `report-2023-2025.12.08` 及 R0 冻结资产集指纹；不可信模板时不产生半完成项目。
- 复制升级新项目完整可用，源项目数据库与文件哈希不变。
- R1 产生的 `full_report` 只处于 `draft`；在 R2 注册完整校验器前，`ready_for_review|confirmed` 一律被稳定错误码阻断。
- 数据库和 API 中不存在总方案第 3.6 节的报告业务字段、中央对象、修正关系或派生内容；阶段边界静态审查通过。
- project_type、workflow_status、导入/导出模式在 Python、TypeScript、数据库和文档中一致。
- 附录 A DOCX、XLSX、导入 roundtrip、校验、预览全量回归通过。
- Ra/Rk Word 零泄漏；批注只产生 warning。
- 安装版升级前备份和恢复路径完成真实验收。
