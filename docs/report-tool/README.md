# 密评报告工具升级实施方案索引

## 1. 文档目的

本目录是“附录A编写工具”升级为“密评报告工具”的权威实施入口。升级工作按 R0 至 R8 九个阶段推进，每个阶段均有独立、可执行、可验收的开发实施方案。

本目录只描述尚未实施的后续工作，不代表对应功能已经完成。现有附录A项目、DOCX 导入导出、Ra/Rk 权威评分、XLSX 打分表和 Windows 客户端能力，在相应阶段完成并通过回归前均保持现状。

## 2. 已确认的产品边界

- 首版只支持当前三级报告模板，规范版本为 `2023`，机构修订版本为 `2025-12-08`。
- 新建完整报告以工具内结构化数据为事实源，Word 是受控复核载体，不是第二套项目数据库。
- 旧项目继续保留附录A模式，并可通过“复制升级”生成新的完整报告草稿；源项目不被修改。
- 正文由确定性模板生成草稿，允许人工改写并追踪与生成基线的偏差；不使用 AI。
- 模板批注只转化为帮助或警告，不直接成为阻断导出的正式规则。
- 正式交付为完整报告 DOCX 和 XLSX 打分表；首版不内置 PDF 输出。
- 附录B首版只接收 PNG/JPEG 图片，不自动转换 PDF、DOCX 或 XLSX。
- 继续依赖 Windows 当前用户账户、目录权限和现有备份机制，不增加项目密码或数据库静态加密。
- 禁止使用 superpowers 插件或其工作流实施本路线。

## 3. 跨阶段统一契约

以下契约一经在 R0 固化，后续阶段不得自行改名或改变语义。确需变更时，必须先更新本索引及所有受影响阶段方案，再实施代码。

### 3.1 项目与流程枚举

| 契约 | 固定值 | 说明 |
| --- | --- | --- |
| `project_type` | `appendix_a`、`full_report` | 旧项目迁移后统一为 `appendix_a`。 |
| `workflow_status` | `draft`、`ready_for_review`、`confirmed` | 单人状态闸门，不引入账户或角色审批。 |
| `template_edition` | `2023` | 规范版。 |
| `template_revision` | `2025-12-08` | 当前机构修订版。 |
| 报告导出模式 | `draft`、`final` | 草稿可不完整但必须带可见标识；最终版受系统不变量约束。 |
| 报告导入类型 | `migration`、`roundtrip` | 既有报告一次性迁移与同源 Word 回收使用不同流程。 |

完整报告新增 API 统一使用稳定项目 UUID 作为路径标识；现有附录A兼容接口继续保留数值 ID，不在同一阶段强制改造。

### 3.2 评分和 Word 边界

- A-1 至 A-4 的 D/A/K/Ra/Rk、对象评分和单元得分继续由后端权威计算。
- A-5 至 A-8 的符合情况和管理单元得分继续由后端权威计算。
- Ra、Rk 只保存于数据库并进入 XLSX 打分表，不进入任何 Word 导入或导出结构。
- 附录A继续保持技术表 8 列、管理表 5 列，不因完整报告升级改变列结构。
- XLSX 导出继续以已保存数据库数据为准，评分未完成时阻断导出。

### 3.3 Word 回收边界

- 日常回收只接受本项目导出的、带有效项目 UUID、导出快照和模板版本的草稿 DOCX。
- 只回收稳定标识的固定字段、受控正文和已有表格行字段。
- Word 中新增、删除、复制或重排业务行不自动应用到项目。
- Word 中新增、替换或删除图片不回收；图片只在工具证据模块管理。
- 检测到未接受修订时阻止回收；Word 批注不写入项目。
- 同一字段在数据库和 Word 中均发生变化时，必须执行基线、数据库、Word 三方比较并逐项解决冲突。
- 不支持的 Word 结构必须形成明确问题，禁止静默丢弃或自动猜测。

### 3.4 最终版导出闸门

以下系统不变量可以阻断 `final`：

- 运行时模板、分节、核心表格或稳定锚点不完整。
- 报告编号、版本、日期、系统名称、被测单位等核心身份字段缺失。
- 附录A评分未完成、存在非法值或权威计算失败。
- 图片、题注、书签或交叉引用断链。
- 一次性迁移仍存在未解决的必确认映射。
- 派生正文因底层数据变化而过期，且用户尚未重新生成或明确确认保留人工版本。
- Word 回收仍存在未解决冲突或来源校验失败。

模板批注提取出的来源核对、编写建议和附录B材料完整性要求只产生 `warning` 或 `info`，不直接阻断最终版。

## 6. 工作包、分支和提交规则

- 每个阶段从最新 `main` 创建独立分支，建议命名为 `codex/report-rN-<scope>`。
- 一个阶段对应一个 Pull Request；一个可独立验证和回滚的工作包对应一个清晰提交。
- 数据库、模板、公共 API 或导入导出契约变化必须先落后端契约与测试，再接入前端。
- 每个工作包至少包含：输入、具体改动、失败行为、测试、验收、提交范围和回滚边界。
- 阶段完成后必须更新本表状态、数据库 schema 版本、模板哈希和 PR 链接。
- 提交前必须检查暂存范围，不得使用 `git add -A` 将根目录真实报告、源模板、XLSX、`.codex/`、storage 或临时文件纳入提交。
- 每个阶段完成后运行阶段测试和 `scripts/run_checks.ps1`，形成清晰中文提交，推送至 `https://github.com/ZN4819/Open-FuLuA.git` 并创建 Pull Request。

## 7. 变更控制

发生下列任一情况时，必须先修改本索引和相关阶段方案，再继续实施：

- 增加新的报告等级或机构模板。
- 改变 Word 回收边界或允许 Word 增删业务行/图片。
- 将模板批注提示升级为阻断规则。
- 引入 AI、多用户权限、PDF 输出或新的证据文件格式。
- 改变 Ra/Rk 的 Word 边界或评分事实源。
- 改变客户端内部 `appId` 或本地数据目录。
