# R6：既有完整报告迁移实施验收记录

## 1. 验收结论

R6 已完成技术实现、全量自动化检查、独立代码复审、Microsoft Word 原生刷新、真实完整报告只读迁移及 Windows 安装态验收，并已创建 [PR #34](https://github.com/ZN4819/Open-FuLuA/pull/34)。当前三级模板族的既有完整报告可以经过“上传只读副本—模板识别—迁移预览—歧义处理—选择附录 A 来源—原子创建新项目—迁移后审阅”流程生成新的 `full_report` 草稿。

本阶段只实现一次性 `migration`，不实现 `roundtrip`；调用后者明确返回不支持。迁移不覆盖现有项目，不修改源 DOCX，不把 Word 中的评分、统计、风险和结论缓存作为权威输入。正文或附录 B 中尚未结构化映射的内容保留原文、来源位置和摘要并进入审阅队列，未处理前阻断正式导出，不发生静默丢弃。

本阶段未使用 LibreOffice。DOCX 结构、分页、字段刷新和兼容性只以 Microsoft Word 原生结果为准。

## 3. 关键实现

### 3.1 模板识别、解析与来源追踪

- 使用 55 张顶层表、一级标题、分节、关键固定文本和附录表结构组成模板指纹；16/17 分节差异不作为单独否决条件。
- 每个结构化候选都必须对应 R2 关联 ID 和权威字段 ID；不能稳定映射的内容以 `ambiguous` 或 `unmapped` 保存，不按位置猜测字段。
- API 对原文展示长度和候选 JSON 大小设限，数据库保留完整本地原文；外部绝对路径和真实报告名称不会进入问题定位信息。
- DOCX 包读取限制单项、总解压量和压缩比；拒绝非法路径、宏、OLE、外部关系以及跨多个 `w:instrText` 拆分的 DDE/DDEAUTO 指令。

### 3.2 附录 A 与权威评分边界

- DOCX 附录 A 必须覆盖 A-1～A-8 的固定结构和 41 个指标单元，缺项、非法评分或孤立 `[[FIG:*]]` 引用时不可作为迁移来源。
- 已有附录 A 项目复制行、评分、图片和交叉引用时重新映射 ID；文件先进入受控暂存区，复制失败或事务回滚时清理半成品。
- 两种来源都由当前后端重算对象分、单元分和指标结论；Word 中的显示分值不覆盖数据库事实。
- 选择已有项目时，未采用的 DOCX 附录候选被明确标记为跳过，不继续形成伪待确认项。

### 3.3 原子确认与迁移后审阅

- 确认事务校验任务 revision、源副本 SHA-256、模板阻断项、附录来源完整性及全部“采用候选”决议；任何失败均不留下半成品项目或孤儿文件。
- 迁移后仍可在项目工作台处理待确认项，但只允许对迁移创建且仍为草稿的完整报告操作。
- 迁移后保存同时校验任务 revision 和项目 `updated_at` 并发令牌，防止较早打开的审阅页覆盖其他页面中的新编辑。
- `adopt_candidate` 只有在目标事实字段实际写入且字段来源为 `adopted` 时才标记为已应用；历史不一致或未应用状态继续显示为可审阅。
- 正式导出校验继续以 `report_field_sources` 的真实映射状态为准，不以客户端显示状态代替后端权威状态。

### 3.4 前端审阅与错误反馈

- 首页增加既有完整报告迁移入口；任务页固定展示模板匹配、章节统计、自动映射、待确认与歧义处理、未识别内容、附录来源与创建确认六个区域。
- 硬阻断诊断保持只读，不能通过手工 resolution 绕过；复合候选必须选择一个标量或人工填写标量，数组和对象不能整体写入事实字段。
- 创建项目后提供稳定迁移审阅深链接；已应用和已跳过项只读，未应用项可继续采用或明确跳过。
- 客户端不使用浏览器本地存储保存决议，刷新后全部状态从后端任务和字段来源读取。

## 4. 代码审查修正

最终代码审查发现并完成以下根因修复：

1. 迁移后审阅最初只校验迁移任务 revision，可能覆盖其他页面中更新更晚的项目字段。现请求同时携带项目更新时间，并在同一 `BEGIN IMMEDIATE` 事务中比较，冲突返回 409。
2. 早期实现可能保留 `adopt_candidate` 决议但目标事实没有写入，导致字段来源仍为 pending、前端却隐藏该项。现预先限制可写事实字段，确认时要求全部采用决议明确入选，写入失败回滚；API 的 `applied` 状态依据实际字段来源计算。
3. 复合候选曾可能把数组整体写入标量字段。现前后端共同限制为非空文本或有限数值，并要求用户明确选择候选或人工填写。
4. 安全扫描曾只检查单个 `instrText`，可能漏过拆分的 DDE 指令。现按 Word 字段边界拼接后检查 DDE 和 DDEAUTO。
5. Windows 路径限制曾按 Unicode 字符数估算。现按 UTF-16 code units 截断并保留确定性哈希，避免非 BMP 字符导致 Word 输出路径越界。
6. 图片复制异常和孤立 FIG token 曾可能留下暂存文件或生成不完整附录。现所有异常路径清理暂存区，孤立 token 直接判定来源不完整。

独立复审未发现剩余 P0～P3 问题。安装包、桌面主程序和后端侧车尚未配置代码签名，这是既有发布链约束，不改变 R6 功能验收结论。

## 6. 阶段闸门与 R7 交接

R6 阶段闸门已具备通过条件：

- 当前三级模板族可稳定识别，16/17 分节和内容控件漂移不会被误判为未知模板。
- 所有已采用事实均可追溯至 R2 字段矩阵；歧义和未识别内容可见、可审阅且阻断正式导出。
- 附录 A 的 DOCX 与已有项目两条来源路径均遵守 Ra/Rk 和后端评分权威边界。
- 确认事务、文件暂存、幂等调用和迁移后并发审阅不会产生半成品、静默覆盖或状态分裂。
- 真实源文件、旧项目和迁移来源数据库均保持不变。
- 全量自动化、Microsoft Word 原生刷新、NSIS 构建和 Windows 安装态验收通过。

R7 可以复用 R6 的安全 DOCX 包扫描、任务/问题/决议模型和迁移审阅界面，但必须继续使用 R4 导出快照实现同源校验与三方差异。R7 不得把一次性迁移任务当作 Word 回收，也不得放宽对修订、图片、业务行或未知 OOXML 的回收边界。
