# 附录A编写工具客户端封装实施计划

> **执行约束：** 每项阶段完成后必须更新本文档和 README，运行对应测试及 `scripts/run_checks.ps1`，形成独立提交并推送到 `https://github.com/ZN4819/Open-FuLuA.git`。涉及桌面运行时、数据目录、安装包或升级逻辑的阶段从 `main` 创建 `codex/desktop-*` 分支。

**目标：** 将现有本地 Web 工具交付为可安装、可升级、可恢复数据的 Windows 客户端，同时保持现有附录A业务与 DOCX 能力。

**总体架构：** Electron 主进程启动 PyInstaller 打包的 FastAPI 侧车；侧车提供打包后的 React 页面和同源 API。业务数据从仓库目录迁移到 `%LOCALAPPDATA%\附录A编写工具`，应用安装、数据迁移、异常恢复和升级互相隔离。

**技术栈：** Electron、electron-builder、React/TypeScript/Vite、FastAPI、SQLite、PyInstaller、PowerShell、Windows NSIS。

## 全局约束

- 仅支持 Windows 10/11 x64，第一版不扩展 macOS/Linux。
- 原始样本文档 `附录A编写.docx` 始终只读，不加入迁移、安装或清理逻辑。
- 客户端数据目录不得位于安装目录，默认使用 `%LOCALAPPDATA%\附录A编写工具`。
- 生产侧车仅监听 `127.0.0.1` 的随机端口，禁止监听 `0.0.0.0`。
- 数据迁移只复制不移动，完成前不得删除源 Web 版数据。
- 任一数据库升级前必须创建可恢复备份；任一迁移必须事务化、幂等并有测试覆盖。
- 阶段提交严禁包含 `storage/`、安装包、临时日志、Word 锁文件和未跟踪的 `附录A导入测试.docx`。

- 前端 API 基址优先级固定为：非空 `VITE_API_BASE_URL`、Vite 开发模式 `http://127.0.0.1:8000`、同源生产模式空基址；显式基址会去除末尾 `/`，其中显式 `/` 仍保留同源覆盖语义，所有请求继续由既有 `/api` 路径构造，不会重复添加前缀。

## CD-4：侧车启动、健康检查和单实例生命周期

### 目标

由 Electron 自动发现侧车随机端口、等待服务就绪、处理退出，并避免双开写库。

### 主要文件

- 新增：`backend/app/desktop_server.py`
- 修改：`backend/packaging/fulua_backend.spec`
- 新增：`desktop/src/backendProcess.ts`
- 修改：`desktop/src/main.ts`
- 新增：`desktop/src/diagnostics.ts`
- 新增：`tests/test_desktop_server.py`
- 修改：`README.md`

### 实施步骤

1. `desktop_server.py` 接收 `--data-root`、`--web-dist`、`--session-token` 参数，在 `127.0.0.1:0` 预绑定 socket 并启动 uvicorn。
2. 侧车监听成功后向 stdout 输出单行 JSON：`{"event":"FULUA_READY","port":12345,"health_url":"http://127.0.0.1:12345/api/health"}`；启动失败输出 `FULUA_FAILED` 并写入日志。
3. `backendProcess.ts` 解析 stdout、执行最多 15 秒的健康检查、收集 stderr 尾部并提供 `start()`、`stop()`、`restartOnce()`。
4. `main.ts` 使用 `app.requestSingleInstanceLock()`；第二次启动仅聚焦已有窗口。
5. 主窗口只在 `start()` 成功后加载侧车根地址；失败时显示诊断页，提供重试、复制诊断、打开日志目录。
6. 正常退出等待 5 秒优雅停止，超时再结束子进程树；异常退出只自动重启一次。
7. 新增 Python 启动器测试和 Electron 单元测试，覆盖就绪消息、端口随机性、超时、重复启动、优雅关闭与一次重启上限。

### 验收与提交

- 用户不需要输入端口；每次桌面启动可使用不同本机端口。
- 连续双击客户端只出现一个窗口和一套侧车服务。
- 强制结束侧车后，客户端显示恢复提示且不无限重启。
- 目标测试、桌面 `win-unpacked` 冒烟启动和 `scripts/run_checks.ps1` 通过。
- 提交建议：`CD-4: 接入客户端侧车进程管理`。

## CD-5：旧 Web 数据迁移、备份与恢复

- 新增：`tests/test_data_migration.py`
- 新增：`tests/test_backups.py`
- 修改：`README.md`

### 实施步骤

1. 定义迁移预检结果：源路径、数据库完整性、项目数、图片数、文件缺失清单、可迁移状态和阻断原因。
2. 实现只读预检：通过 SQLite 备份 API 处理 WAL，执行 `PRAGMA integrity_check`，校验 `evidence_images.file_path` 是否存在。
3. 实现复制迁移：写入 `migration/staging-{uuid}`，复制数据库和 storage，生成 SHA-256 清单后原子改名为正式目录。
4. 写入 `migration-state.json`，记录源路径、开始/完成时间、统计摘要、工具版本和失败原因；不得记录项目正文。
5. 实现备份：数据库使用 SQLite backup API，storage 使用变更文件清单和硬链接失败后的复制回退；保留策略为 7 份日常、3 份升级前、3 份迁移前备份。
6. 实现恢复：先创建当前快照、停止写入、替换数据库和 storage、校验后要求侧车重启。
7. 在客户端首次启动流程中提供新建数据和迁移数据入口；迁移失败仍可选择新建空数据，源数据始终保留。

### 验收与提交

- 迁移 fixture 后，项目、章节、测评行、图片、图号和交叉引用数量与源数据一致。
- 故意损坏源数据库或缺少图片时，预检阻断迁移并保留源目录。
- 恢复测试能回到指定备份的项目和图片状态。
- 目标 pytest、手动迁移回归和 `scripts/run_checks.ps1` 通过。
- 提交建议：`CD-5: 增加客户端数据迁移与恢复`。

## CD-7：异常恢复、升级检查与发布链路
